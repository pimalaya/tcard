# A collision is duplicate TOML keys

The `merge` verb landed beside `template` and `edit`: three card paths in, one vCard path out, the merge run in process and its outcome projected as the same TOML form the other verbs edit. What the merge settled is already in the document; what it could not is written twice, once per side, which TOML refuses to parse. Nothing is written until the reader has deleted a line.

## The bridge

The proposal called the merge "a function it already links", which was not literally true: tCard projects through calcard, and the three-way merge lives in vcard-rs, over its own byte-faithful tree. Migrating off calcard was never worth it and never happened. The two coexist, joined at their only common form, the vCard bytes: the three inputs parse as `VcardCst`, `vcard::tree::merge::merge` runs, `report.merged` serializes back to a card, and that card goes through the existing calcard parse and TOML projection. vcard-rs is a new dependency behind an opt-in `merge` feature that `cli` pulls in, so the slim `no_std` projection library does not grow a second vCard parser by default.

## Addressing a key from a report action

The merge report names the field each side moved, and the projection names the key each field is written under; the whole change is the map between them. A whole-value change addresses the field's own key for a bare field and `value` inside the instance table for a typed one. A `ValueComponentChanged` addresses the component's own key, which is what keeps a contested street inside its one `[[address]]` block: the decomposition is the report's, not ours, and two sides editing different components of one address never collide in the first place. A `TYPE` parameter addresses `type`. Everything else has no key to contest and falls through to a note.

Values are rendered as the projection would render them, an array for a list field and a quoted string elsewhere, by encoding the reported value back through vcard-rs and decoding the leaf out of it. A date renders as its RFC 6350 string rather than a native TOML date; `apply` reads either back, so the applied card is the same either way.

Placement is by value, not by index. A report path indexes an instance in the *base* card, and the merged card is the local one with the remote's actions replayed, so the two orders are not the same and the mapping between them is not exposed. The contested line is instead found by scanning the field's blocks for the key holding the value the merge kept, which is the local one in every case that renders as a choice. A line already contested by another collision is skipped, and the rewrites are applied from the bottom up so an earlier index stays where it was located.

## What the header says instead

Three things are said in a comment continuing the document's own header rather than as a choice:

- **A removal against an update**, which the merge already decided in favour of the update. There is nothing to pick, and the removed side has no line to write.
- **A collision on a part the document does not show**: an unmodeled property (a custom `X-*`), a parameter other than `TYPE`, a whole-value change on a structured field, a component the version hides (`pobox` and `ext` in 4.0). The local value was kept and the note says so. This is the honest fallback, not a decision: the alternative is inventing a key the projection has no place for.
- **An instance paired by position**. The report does not say how the pairing was made, so it is inferred: the base card holds several properties of that name and the collided one carries no `PID`, which leaves order as the only thing the pairing could have rested on. It is deliberately quiet when there is one instance of the name, where position is unambiguous.

## Refusing an undecided document

`merge::apply` wraps the existing `template::apply` and rewrites one error. toml_edit reports a repeated key as `duplicate key` with a span and no name, so the key is read back out of the edited buffer at that span, and the error becomes `TcardError::Undecided` naming the field. The CLI treats it exactly like a broken buffer: the `edit` verb's reprompt loop, now shared by both verbs as `edit_toml`, re-opens the editor seeded with the user's own buffer, so a half-made decision is never lost. The output path is written only after the fold succeeds.
